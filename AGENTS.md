# AGENTS.md

ESP32 course projects (Electronics Design curriculum). Each top-level directory is a separate ESP-IDF project; there is no root build.

## Environment & build

- ESP-IDF v5.4.4, target `esp32s3`, 2MB flash. Toolchain lives at `~/.espressif/v5.4.4/` (not on PATH by default).
- To build/flash a project (e.g. `blink-led`):
  ```sh
  source ~/.espressif/v5.4.4/esp-idf/export.sh
  cd blink-led && idf.py build        # then: idf.py flash monitor
  ```
- No tests, linter, or CI in this repo. `idf.py build` is the only verification.

## Conventions & gotchas

- `managed_components/` (downloaded deps, e.g. `espressif__led_strip`) and `sdkconfig`/`sdkconfig.old` are committed. Never hand-edit them; change `main/idf_component.yml` instead and let `idf.py` regenerate.
- Wiring tables in `README.md` are the source of truth for hardware connections; keep them in sync with the pin defines in `main/*.c`.
- Board is an ESP32-S3-WROOM-2 (32MB octal flash): GPIO33-37 are taken by the flash and must never be used. GPIO0/3/45/46 are strapping pins; 19/20 are USB-JTAG (wired to the USB connector); 38 is the DevKitC-1 v1.1 onboard RGB LED; 43/44 are the UART console. Encoder pairs must stay on clean pins (A=41/40, B=8/3, D=17/18; E2B on GPIO3 is a strapping pin but works as input).
- New projects follow `idf.py create-project <name>` + `sdkconfig.defaults` (`CONFIG_ESPTOOLPY_FLASHSIZE_2MB=y`) + `idf.py set-target esp32s3`.
- Project roles: `blink-led` reads the LQ-R4CHVB 4-channel line sensor (GPIO11-14, 0=black 1=white, CH1 rightmost). `motor-test` drives the 3 TB6612 motors with encoder PID speed control and owns `set_speed(vx, vy, wz)` (cm/s, cm/s, rad/s, ROS2 frame: x forward, y left, CCW+; omni wheels, drive dirs A=30° B=270° D=150°, base 9 cm, 512 counts/wheel-rev measured (spec "512 AB" already includes ×4), wheels 5.5 cm). `line-follow` reuses the same PID closed loop + `set_speed` (kept in sync by copy-paste) plus the line sensor for black-line following (rotate in place with vx=0 when the 4 sensors are asymmetric, PD on wz, forward only when symmetric, stop on all-white). `encoder-test` only reads the 3 wheel encoders (no motor output) to verify PCNT counts by hand. `web-ctrl` is another copy of the motor-test PID/`set_speed` core plus WiFi AP (`ESP32-CAR` / `12345678`, IP 192.168.4.1) serving a button web page on `/` and a `GET /cmd?vx=&vy=&wz=` API with a 600 ms command-timeout watchdog. `camera-test` uses the managed component `usb_host_uvc` (libuvc, ^1.0.4) to read a USB UVC webcam on the native USB port (GPIO19/20), negotiates 320x240/640x480 MJPEG (frame buffer capped at 64 KB, board has no PSRAM; 1280x720 MJPEG does not fit), and serves it to the browser as a static JPEG snapshot on `/frame` (the HTML page polls it onload-chained, one request at a time, and displays it rotated 180° via CSS because the camera is mounted upside down — server-side rotation is impossible without PSRAM; multipart streaming proved unreliable with this camera/browser). AP `ESP32-CAM` / `12345678`. Requires `CONFIG_USB_HOST_CONTROL_TRANSFER_MAX_SIZE=16384` for large camera descriptors. The user's camera (349c:3307) puts VS class descriptors after the endpoint, so `camera-test/managed_components/espressif__usb_host_uvc/src/descriptor.c` carries a local patch (attach post-endpoint descriptors to the interface extra) and `src/libusb_adapter.c` carries two more (round IN transfer sizes up to the endpoint's OWN MPS, not the interrupt endpoint's; read string descriptors from the enumerated device info instead of issuing control transfers, which hang on this camera and crash `usbh_dev_close`), and `libuvc/src/stream.c` carries one (detect raw-JPEG streams with no UVC payload headers and skip header parsing) — all would be lost if the component is regenerated. `camera-task` waits 2 s after the UVC_DEVICE_CONNECTED event to avoid a `usbh_dev_close` assert race with enumeration. `cam-ball-track` reuses the same camera stack (patched component files were copied from `camera-test/managed_components/` — the registry was unreachable when it was created) and the line-follow motor core; it decodes only the JPEG DC coefficients (no IDCT, no dequant, fits without PSRAM) to build a 16x16-block Cr/Cb map, finds red blocks (cr high, cr-cb high), computes the centroid, and PD-controls wz to aim the car at the ball (camera mounted upside down, sign handled by `CAMERA_FLIPPED`).
- Build artifacts (`build/`) are gitignored.
